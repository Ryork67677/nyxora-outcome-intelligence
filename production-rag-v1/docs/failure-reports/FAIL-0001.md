# FAIL-0001 — EXP-000 lexical retrieval returned nothing at all

**Status:** diagnosed and fixed
**Stage that failed:** lexical query construction (`rag_v1.retrieval.lexical_search`)
**Corpus snapshot:** `snap_689e336380a054d8039dc35b2c09cd0a` (202 documents, 14,209 chunks)
**Experiment:** EXP-000, k = 10, 20 retrieval-scored golden cases
**Archived failing run:** `experiments/EXP-000/results-websearch-and.json`

## Symptom

The first EXP-000 run reported `macro_recall = 0.000`. Not "low" — zero, on every
one of the 20 cases. The distinguishing detail was in the per-case records:

```
AN-001 recall 0.0 hits_returned 0
AN-002 recall 0.0 hits_returned 0
AN-003 recall 0.0 hits_returned 0
```

`hits_returned = 0` rules out an evidence-matching bug. Nothing was being scored
because nothing was being retrieved. That moves the investigation from
`score_evidence` to the SQL that produces candidates.

## Exact point of failure

`lexical_search` built its query with `websearch_to_tsquery('simple', question)`.
That function **ANDs** every token it produces. Asking Postgres directly:

```sql
SELECT websearch_to_tsquery('simple',
  'Which HTTP status code does the Claude API return with the request_too_large error type?');
```

```
'which' & 'http' & 'status' & 'code' & 'does' & 'the' & 'claude' & 'api' & 'return'
 & 'with' & 'the' & 'request' <-> 'too' <-> 'large' & 'error' & 'type'
```

```sql
SELECT count(*) FROM chunk c WHERE c.search_vector @@ websearch_to_tsquery('simple', '...');
-- 0
```

Every one of those sixteen tokens had to appear inside a single chunk. The
`simple` text search configuration — chosen deliberately so technical
identifiers are not damaged by stemming — has **no stopword list**, so `which`,
`does` and `the` were mandatory match terms too. No chunk in a 14,209-chunk
corpus satisfies that conjunction, so the GIN index correctly returned the empty
set for all 20 questions.

This is a query-construction bug, not a corpus bug. Corpus health was verified
separately: all 202 versions ingested with status `current`, and all 14,209
chunk spans round-trip exactly against `normalized_text` (0 mismatches).

## Hypothesis

A natural-language question is a bag of evidence terms, not a conjunction. The
retriever should score chunks by how much of the question's *informative* content
they cover, weighting rare terms above common ones.

## Changes made, and what each one bought

Measured in sequence on the same snapshot and the same 20 cases at k = 10.

| Step | Lexical query construction | macro span recall | cases fully recalled |
|---|---|---:|---:|
| 0 (as shipped) | `websearch_to_tsquery` (AND) | 0.000 | 0/20 |
| 1 | OR the terms, rank with `ts_rank_cd` | 0.125 | — |
| 2 | + drop terms with df > 10% of corpus, rank normalization 1 | 0.325 | — |
| 3 (kept) | BM25 over the same TSVECTOR/GIN index | **0.475** | **9/20** |

Step 1 was necessary but not sufficient. With OR semantics and `ts_rank_cd`,
which has no inverse document frequency, ubiquitous terms decided the ranking.
For AN-002 the top hit was an unrelated benchmark citation block, because it
matched many common words:

```
r1 s=11.50 ['Benchmarks referenced']  '1. **WideSearch:** Wong et al., "WideSearch: ...'
r2 s=11.40 ['Model compatibility']    '| Executor models | Advisor models | ...'
```

Step 3 addresses that directly. BM25 weights a term by `ln(1 + (N-df+0.5)/(df+0.5))`,
so in the AN-002 query `request_too_large` (df 59) outweighs `type` (df 5,494)
by construction. This is **not** a scalar identifier boost — no rule mentions
identifiers at all; the identifier simply happens to be the rarest term. Term
frequency is treated as binary presence per chunk, which is what a TSVECTOR match
gives cheaply, and BM25 length normalization is retained so long reference tables
stop outranking short precise statements purely by size. `k1 = 1.2`, `b = 0.75`
are the standard defaults and were **not** swept against the golden set.

Identifier handling is preserved end to end: query terms keep `_`, `.` and `-`
inside a token, and each term becomes a `phraseto_tsquery`, so `request_too_large`
matches as the adjacent phrase `'request' <-> 'too' <-> 'large'` rather than as
three independent words.

## Regressions introduced

None against the archived baseline — it scored 0.000 on every case, so no case
could regress. The fix is a strict improvement on all 20 cases.

Two second-order effects are worth recording rather than hiding:

* BM25 length normalization penalises very long chunks. That is the intended
  behaviour, but it interacts badly with the oversized reference chunks
  documented in FAIL-0002.
* Query terms are no longer required to co-occur, so the candidate pool is much
  larger. Latency for the 20-case evaluation went from ~2 s to ~6 s. At this
  corpus size that is irrelevant; at a much larger corpus the per-term `df`
  lateral subquery would need caching.

## Verification

```
pytest -q            # 12 passed
ruff check .         # All checks passed!
```

`tests/test_lexical_query.py` pins the query-construction behaviour that this
report is about: identifiers survive as single terms, dotted and hyphenated
identifiers are kept whole, and punctuation-only tokens are discarded. That last
test caught a real defect while it was being written — `--` passed the original
length filter — which is now fixed by requiring an alphanumeric character.

## What this failure does **not** license

EXP-000 is now a working lexical baseline, not a good one. 9 of 20 cases are
fully recalled. The next failure is a different stage and is written up
separately in FAIL-0002; it should be read before anyone proposes a reranker.
